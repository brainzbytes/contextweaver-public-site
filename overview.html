Travel story

“Book me a policy-compliant flight to Seattle next Tuesday and send me the itinerary.”

OutcomeA confirmed trip—not a list of links.

The traveler receives an approved itinerary, booking reference, calendar entry, and notification. The business receives the policy, approval, payment, and booking evidence.

SolutionBusiness Travel Assistant

The final experience the traveler opens and uses.

ServicesTrip planning · Booking · Payment · Notification

Reusable business outcomes with typed inputs and results.

WorkflowsSearch → compare → approve → reserve → pay → confirm

Durable steps that can wait, retry, or compensate safely.

AgentsTravel planner · Policy specialist

Bounded reasoning specialists that interpret choices and propose a plan.

MCP capabilitiesAirline · expense policy · traveler profile · payment · calendar · email

Governed access to the systems that can read data or take action.

  • Ask

    The traveler states dates, destination, preferences, and the desired result in ordinary language.

  • Understand

    Identity, role, traveler profile, loyalty numbers, company travel policy, budget, calendar, and purpose are gathered from approved sources.

  • Plan

    The Travel Agent compares viable flights and proposes an exact itinerary using approved airline and policy capabilities.

  • Authorize

    Policy checks cabin, price, route, and purpose. An out-of-policy choice pauses for the traveler or manager to approve.

  • Execute

    The Workflow reserves the seat, brokers a scoped payment credential, confirms the booking, writes the calendar event, and sends the itinerary.

  • Prove

    The result includes the selected fare, policy decision, approval, booking locator, payment receipt reference, messages sent, and complete run history.

  • Improve

    Latency, failures, retries, price changes, traveler feedback, and provider reliability help improve future runs without silently changing authority.

Guardrails a person can understand
  • The Agent can recommend a flight; it cannot invent permission to buy it.
  • Payment credentials stay in a trusted gateway and are never exposed to the Agent.
  • Price or itinerary changes beyond the approved scope require a new decision.
  • A failed booking can release the reservation or reverse the charge through compensation.
What is gathered as evidence
  • Who asked, for what purpose, and under which role
  • Options considered, citations, policy rules, and the chosen plan
  • Approval and entitlement decisions
  • Tool receipts, booking and payment references, logs, metrics, and traces
Software delivery story

“Implement this approved specification, add tests, commit it, and open a pull request.”

OutcomeA reviewable pull request tied back to the specification.

The developer receives code, tests, build results, a commit, and a PR. Reviewers receive traceability from each requirement to the changed files and validation evidence.

OverviewJourneyWhat powers itGuardrails and evidence
SolutionGoverned Software Delivery Assistant

The developer experience from approved specification to review.

ServicesChange implementation · Validation · Pull-request delivery

Reusable contracts for producing and reviewing a software change.

WorkflowsAnalyze → branch → edit → test → scan → commit → open PR

A durable delivery path with explicit gates and recovery.

AgentsSpec analyst · Coding Agent · Test Agent · Review Agent

Specialists with separate responsibilities and bounded tools.

MCP capabilitiesSpecification · repository · work items · CI · security scanner · artifact registry

Least-privilege access to engineering systems.

  • Ask

    The developer selects an approved specification and asks for a complete, review-ready implementation.

  • Understand

    The platform gathers repository instructions, architecture, code owners, work items, dependency rules, test conventions, and protected-branch policy.

  • Plan

    The Spec Analyst maps requirements to components. The Coding and Test Agents propose file changes, tests, and validation commands.

  • Authorize

    Policy verifies repository access, allowed tools, branch scope, change risk, data classification, and whether a human must approve execution.

  • Execute

    The Workflow creates a branch, edits only permitted files, runs tests and scans, records results, commits with traceability, and opens the PR.

  • Prove

    The PR links requirements, code changes, test output, security findings, model and capability versions, approvals, and the immutable execution plan.

  • Improve

    Review feedback, escaped defects, flaky tests, build time, and acceptance results improve evaluation and planning—not branch protection or approval rules.

Guardrails a person can understand
  • The Coding Agent works only in the approved repository, branch, and file scope.
  • Protected branches remain protected; the platform opens a PR but does not autonomously merge it.
  • Code generation and independent review use separate identities and evidence.
  • Secret scanning, dependency checks, tests, and required reviewers still apply.
What is gathered as evidence
  • Specification revision and requirement-to-code mapping
  • Repository digest, branch, changed files, prompts, and capability versions
  • Test, lint, build, security, and policy results
  • Commit SHA, PR link, reviewer decisions, logs, metrics, and traces

“Prepare Acme’s renewal, propose the right offer, update the CRM, and schedule the follow-up.”

OutcomeA prepared renewal with approved next actions.

The account owner receives a concise account brief, recommended offer, updated opportunity, drafted outreach, and scheduled follow-up—without losing control of pricing or customer communication.

SolutionAccount Growth Assistant

The seller-facing workspace for renewals and customer growth.

ServicesAccount insight · Offer preparation · CRM update · Outreach

Reusable outcomes shared across sales Solutions.

WorkflowsGather → assess → recommend → approve → update → communicate

A repeatable process that keeps pricing and outreach governed.

AgentsAccount Analyst · Offer Agent · Compliance Reviewer

Specialists that summarize, reason, and recommend within policy.

MCP capabilitiesCRM · product usage · support history · pricing · contracts · calendar · email

Identity-aware access to customer and commercial systems.

  • Ask

    The account owner requests a renewal plan for a named customer and target date.

  • Understand

    The platform gathers the customer record, contract, usage, open issues, previous commitments, renewal policy, pricing authority, and communication history.

  • Plan

    The Account Analyst summarizes health and risks. The Offer Agent proposes the next-best action, package, and outreach sequence with cited reasons.

  • Authorize

    Discount, data-use, legal, territory, and communication policies determine what the seller can approve and what must go to finance, legal, or management.

  • Execute

    The Workflow updates the opportunity, creates tasks, prepares the quote, drafts the email, and schedules the meeting. Sending or discounting waits for required approval.

  • Prove

    The account record shows source data, cited insights, policy decisions, approved offer, CRM changes, communications, and the resulting customer response.

  • Improve

    Conversion, response, forecast accuracy, discount effectiveness, stale data, and customer feedback improve recommendations and operational health.

Guardrails a person can understand
  • The Agent may recommend a discount but cannot exceed the seller’s authority.
  • Customer data is filtered by identity, role, account ownership, and purpose.
  • External messages remain drafts until the appropriate person approves sending.
  • Every CRM change records the old value, new value, reason, and actor.
What is gathered as evidence
  • Customer sources, timestamps, citations, and data-access decisions
  • Account-health calculation and offer rationale
  • Discount, legal, and communication approvals
  • CRM mutations, quote versions, messages, outcomes, logs, metrics, and traces
Customer care story

“This customer was charged twice. Verify it, fix it, and explain what happened.”

OutcomeA resolved case with a clear explanation and proof.

The customer receives an accurate response and, when authorized, a refund. The service team receives a complete case history, policy basis, financial receipt, and operational signals.

SolutionCustomer Resolution Console

The agent-facing experience for understanding and resolving cases.

ServicesCase triage · Billing investigation · Refund · Customer notification

Reusable resolution outcomes with controlled side effects.

WorkflowsClassify → verify → investigate → approve → resolve → notify → close

A durable case path that can pause for people or external systems.

AgentsCase Triage Agent · Billing Specialist · Response Agent

Specialists that reason over the case without owning financial authority.

MCP capabilitiesTicketing · CRM · orders · billing · payment · policy knowledge · messaging

Governed connections to customer and transaction systems.

  • Ask

    A customer or service representative reports the duplicate charge and asks for resolution.

  • Understand

    The platform gathers the authenticated customer, case history, order, invoice, payment events, refund policy, communication preference, and agent authority.

  • Plan

    The Billing Specialist compares the order and payment timeline, determines whether the charge is duplicate, and proposes the permitted remedy.

  • Authorize

    Policy checks refund amount, transaction age, fraud signals, customer identity, service-agent limits, and whether supervisor approval is required.

  • Execute

    The Workflow issues the authorized refund, updates the ticket and CRM, sends the explanation, and schedules follow-up if settlement is delayed.

  • Prove

    The closed case includes the payment comparison, policy applied, approval, refund receipt, customer message, timestamps, and full run history.

  • Improve

    Repeat incidents, refund latency, escalation rate, customer sentiment, and payment-provider errors become observable signals for product and operations teams.

Guardrails a person can understand
  • The Agent can diagnose and recommend; only policy-authorized capabilities can issue money.
  • Customer identity and account ownership are verified before private data is exposed.
  • High-value or suspicious refunds pause for independent approval.
  • Messages cite verified transaction facts instead of inventing an explanation.
What is gathered as evidence
  • Customer, case, order, invoice, and payment-event lineage
  • Diagnosis, policy version, authority, and approval decision
  • Refund transaction and downstream update receipts
  • Customer communication, settlement status, logs, metrics, traces, and outcome
What stays the same in every example

The domain changes. The trust model does not.

Identity follows the request. The platform knows who is acting, for what purpose, and under which role and entitlements.

Models propose; policy authorizes. An Agent can reason about a plan, but it cannot grant itself access, credentials, approval, or authority.

Work survives interruption. Durable Workflows can wait for approval, retry transient failures, resume, or compensate completed steps.

Every important step leaves proof. Plans, citations, decisions, approvals, receipts, artifacts, metrics, logs, traces, and outcomes remain connected.
